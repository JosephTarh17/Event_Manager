----------------------------------------------------------------------------

What it means:

6. Rendering arrays with map()
----------------------------------------------------------------------------
What we did:
- Stored sample event objects in an events array.
- Used events.map((event) => <EventCard ... />).
- Passed event fields to EventCard as props.
- Added a key using event.id.

What it means:
map() visits each item in an array and returns a new array. In JSX, it is used to turn data objects into React components.

The key prop is a React identifier for each list item. It should be stable and unique, normally a database ID.

Example:
events.map((event) => (
  <EventCard key={event.id} title={event.title} />
))

7. React state for events
----------------------------------------------------------------------------
What we did:
- Changed the sample events array into state:
  const [events, setEvents] = useState([...])
- Added an addEvent function.
- Called setEvents with a functional updater.
- Used the spread syntax to keep existing events and create a new array.
- Connected addEvent to the New event button with onClick.

What it means:
State stores values that React tracks and rerenders when they change. setEvents updates event state and rerenders the event list.

The functional form reads the latest state:
setEvents((currentEvents) => [
  ...currentEvents,
  newEvent,
])

The spread syntax copies existing array items into a new array. React state should be updated immutably: create new arrays or objects instead of editing state directly.

8. Controlled search input
----------------------------------------------------------------------------
What we did:
- Added a query state value.
- Bound the search input value to query.
- Updated query from the input's onChange event.
- Filtered events before rendering them.

What it means:
A controlled input stores its value in React state. When the user types, React updates state and the JSX rerender displays the current value.

Example:
const [query, setQuery] = useState('')

<input
  value={query}
  onChange={(event) => setQuery(event.target.value)}
/>

13. Controlled event form and API-backed submission
----------------------------------------------------------------------------
What we did:
- Added isFormOpen state to control whether the New event form is visible.
- Added draftEvent state for title, topic, date, and status values.
- Connected the New event button to setIsFormOpen(true).
- Added controlled title, topic, and date inputs that update one draft field
  while preserving the other fields.
- Added required attributes so the browser checks that the fields are filled.
- Connected the form's onSubmit event to the API-backed saveEvent handler.
- Called event.preventDefault() to stop a normal browser form submission/reload.
- Sent the draft to POST /api/events and appended the saved document returned
  by MongoDB, including its database-generated _id.
- Reset the draft values and closed the form after submitting or cancelling.

What it means:
- Boolean state can determine whether a section of JSX is rendered:
  {isFormOpen && <form>...</form>}
- A controlled input gets its current value from React state and updates that
  state in onChange.
- A form submit handler receives the submit event. preventDefault() keeps the
  browser from navigating/reloading so React can handle the submission.
- Native required validation prevents an incomplete form from submitting.
- The new event is appended immutably, so React receives a new array reference
  and rerenders the list.
- The frontend talks to Express with fetch; Mongoose saves the document to
  MongoDB, and the API response is used to update React state.

Validation:
- Oxlint passes.
- Vite production build passes.
- The user tested creating an event in the browser: the form submitted
  successfully, closed, and the new event appeared.
- The required-field behavior was included in the test checklist.

Next concepts:

- Check API responses before treating a request as successful.

14. Callback props and deleting list items
----------------------------------------------------------------------------
What we did:
- Passed each event's id and the deleteEvent function from App to EventCard.
- Attached an onClick handler to the delete button in EventCard.
- Called onDelete(id) from the child component when the user clicked delete.
- Implemented deleteEvent inside App, where it can access setEvents.
- Sent DELETE /api/events/:id and only removed the row from React state after
  the API confirmed deletion.
- Used Array.filter() to produce a new events array without the selected ID.
- Verified deleting an event in the browser.
- Refreshed the page to confirm the deleted event stayed deleted.
- Confirmed Oxlint and the Vite production build pass.

What it means:
A callback prop is a function passed from a parent component to a child.
The child can call it to tell the parent that an action occurred. Here,
EventCard does not own the events array; it asks App to delete an event.

The state owner keeps state updates in one place:
App -> EventCard(onDelete) -> App.deleteEvent(id) -> API DELETE -> MongoDB
-> setEvents(newArray)

Array.filter() returns a new array containing only items that pass a test.
Using filter to remove an item is an immutable update: the original state
array is not edited in place.

JavaScript scope lesson:
deleteEvent must be declared inside App to use App's setEvents variable.
Functions outside App cannot access variables created inside App. The build
and linter may not catch every scope/runtime issue, so test interactions too.

17. Mongoose Event schema and model
----------------------------------------------------------------------------
What we did:

19. Event API CRUD routes and HTTP responses
----------------------------------------------------------------------------
What we did:
- Kept GET /api/events to list documents and POST /api/events to create one.
- Added GET /api/events/:id, PUT /api/events/:id, and DELETE
  /api/events/:id.
- Validated MongoDB IDs before looking up, updating, or deleting a document.
- Returned 400 for malformed IDs, 404 when no document exists, 201 for
  creation, 200 for reads/updates, and 204 for successful deletion.
- Used runValidators on updates so Mongoose schema rules apply.
- Tested create, read-one, update, delete, and read-after-delete using a
  temporary test event; the test event was deleted.

What it means:
CRUD means Create, Read, Update, and Delete. HTTP methods communicate the
requested action: POST creates, GET reads, PUT updates, and DELETE removes.
The `:id` route segment is a parameter read from the URL. The route calls the
Mongoose model, which performs the database operation. The API response status
distinguishes success, invalid input, and a missing record.

The frontend is connected to these routes: it loads the event list with GET,
creates with POST, updates with PUT, and deletes with DELETE. The GET response
uses MongoDB's _id for React keys and item actions.
